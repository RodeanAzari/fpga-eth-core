## Interpretation

The gate's criterion is zero drops (`~/fpga-coord/dependencies.toml`). Every datagram the host
sent was delivered byte-exact (`udp_ok` = sent, `payload_bytes` exact) with no FIFO overflow,
over 10 minutes at 98.4% of line rate, which is the highest rate the link carries with 1,472-byte
payloads (ceiling 8,127/s). The RX FIFO never held more than a few bytes: the 125 MHz core
drains it about ten times faster than 100 Mbit/s fills it, so the 2,048-byte FIFO has a large
margin at this rate. The high-water mark reflects steady streaming only; it does not bound the
occupancy under core-side backpressure, which this example never applies.

`seq_err` is non-zero because the host reorders about 0.08% of datagrams before they reach the
wire, so some arrive out of order; none are lost. Evidence, from short 80,000-datagram runs with
the same sender:

- WSL egress (`tcpdump -i eth0`): 80,000 of 80,000 in order.
- Windows `pktmon` along the transmit path, followed by IP ID: no reordering through vmswitch;
  it first appears at `netadaptercx.sys` (the I225-LM miniport). The capture
  (`C:\Users\rodea\fpga_capture\`, 240 MB) is not committed.
- WSL `ethtool -L eth0 combined 1` did not remove it.

Consumers that need in-order delivery (MoldUDP64, P2 Phase D) need a host path that doesn't
reorder; that is a host issue, not an fpga-eth-core one.
