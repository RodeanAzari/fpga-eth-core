# fpga-coord 0005 on the board, 2026-11-13: the acceptance test passes; the fault still does not reproduce here

Question: does the fix (`rx_reset_bridge` in `eth_rx`, `2b803fe`, plus the example's MDIO
link gate) pass the acceptance test in request 0005, and can the fault be produced on
demand on this board so the fix can be shown to cure it?

**Answer:** the acceptance test passes (100 / 100 reprogram-then-stream cycles, FIFO
high-water mark never above 1 byte). The fault did not appear in any of 330 cycles on the
fixed or the unfixed core, including a test build meant to provoke it. So this board still
cannot show that the fix cures P3's fault; the mechanism and the fix are shown in
simulation (`tb/test_eth_rx_reset.py`, `a35b0dc` and `2b803fe`).

## Interpretation

- **Acceptance test:** passes as written in the request (100 reprogram-then-stream cycles,
  `fifo_level` never above 2,048; here the high-water mark never passed 1 byte, and every
  datagram arrived). As on 2026-11-11, the unfixed control is clean too, so this run shows
  the fix does no harm; it cannot show the fix cures the fault.
- **The 6 control failures without settle are a harness artifact, not the fault:** each
  missed 1,531 to 1,785 datagrams, all before the first one received (`seq_err` =
  `seq_lost` = 0, `fifo_hwm` 1). The v0.2 MAC starts 200 ms after reset whatever the link
  is doing, so the harness started sending before the link came up. With a 3 s settle,
  100 / 100 pass. The fixed example waits for MDIO link up (MAC up at 4.2 s, not 2.3 s),
  so it needs no settle.
- **The provoking build did not corrupt.** In simulation the fault needs the MAC's core
  side to reset while rx_clk is stopped, leaving the FIFO's write pointer at its old value.
  Here the core side resets and leaves reset 800 ms before the PHY does. After 4,000
  datagrams the old write pointer is almost never 0, so the fault would read as a level far
  above 1. Every cycle reads 1, so the write side did reset. The likely reason is that the
  DP83848J keeps driving RX_CLK while its reset pin is low on this board, so the example's
  rx-domain reset synchronizer still moves. **Not verified:** that needs a counter on
  rx_clk during PHY reset. If it holds, holding the PHY in reset cannot provoke this fault
  on the Arty, and P3's trigger is something else that stops or upsets rx_clk (their
  questions (3) and (4) in the request are still open).
- The matching fix-side provoking build (`LINK_GATE=0`, 1 s PHY reset, SHA-256 prefix
  `67ba1f2d6ee71412`, WNS +0.635 ns) was built but not run: with the control clean, it
  could not discriminate.
